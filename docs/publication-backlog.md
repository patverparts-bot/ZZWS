## Развёрнуто с дополнительной проверкой

**PUB-002 — ограничение фактического размера multipart-загрузок.** Опубликовано в API 81: добавлен `body-reader.mjs`, изменены только `index.ts`, `order-routes.mjs` и `report-routes.mjs`; остальные 64 файла сохранены. После публикации все 68 файлов скачаны и сверены. Миграция не требуется.

Семь изолированных проверок подтвердили границы размера, отсутствие/ложный Content-Length, незавершающуюся отмену потока, все четыре маршрута, авторизацию и сохранность вложений. На рабочем сервере небольшой некорректный multipart возвращает ожидаемый HTTP 400. Однако большие живые запросы завершились по тайм-аутам; журналы содержат WallClockTime при низком CPU. **HTTP 413 для большого запроса в рабочей среде пока не подтверждён. Пункт не считается полностью закрытым.** Точный источник ожидания тела/транспорта не установлен; приписывать это старому запросу публикации нельзя.

Следующий шаг: отдельно установить причину ожидания большого тела запроса и подтвердить живой HTTP 413, не создавая реальных заказов, отчётов или опубликованного прайса. Новые большие загрузки автоматически не повторять. Подтверждения: [проверки кандидата](../work/backlog-ready-release/multipart-validation.json), [исходники API 81](../work/backlog-ready-release/api-source-readback.json), [малый живой запрос](../work/backlog-ready-release/small-upload-probe.json), [диагностика больших запросов](../work/backlog-ready-release/multipart-live-diagnostic.json).

## Как обновлять реестр

1. Для каждого нового отложенного изменения добавить устойчивый ID, понятное название, затронутые части, место сохранения исходников, выполненные проверки, конкретную причину остановки и следующий шаг.
2. Разделять подготовку исходников, локальные проверки, публикацию исходников в ветку и включение в рабочей среде. Не обозначать все эти состояния словом «готово».
3. Зависший процесс отмечать отдельным блокером с датой, идентификатором запроса или процесса, затронутым каналом и последним подтверждённым состоянием. После успешного выпуска перепроверять старый блокер, а не переносить его автоматически.
4. Перед возобновлением перечитать текущие серверные исходники, версии и миграции, сверить `main`, совместить только нужные изменения и повторить необходимые проверки. Старый подготовленный пакет не должен откатить более поздние исправления.
5. После фактической публикации и проверки рабочего результата перевести пункт в опубликованные, записать коммит, версию и подтверждение. Не удалять историю причины остановки.

При инвентаризации сравнены 160 верхнеуровневых публичных файлов сайта и админки; [различия](../work/publication-backlog-audit/source-differences.json) и [добавленные локальные файлы](../work/publication-backlog-audit/local-files-absent-main.json) сохранены для повторной сверки. Само расхождение файла не считается отдельной неопубликованной функцией: локальный файл может быть старее рабочего или содержать несколько пакетов. Исторические заметки и неподтверждённые различия не выдаются за готовые выпуски.
