## История устранения тайм-аута загрузок

**PUB-002 — ограничение фактического размера multipart-загрузок. Опубликовано и проверено в API 82.** Первоначальная API 81 добавила общий `body-reader.mjs` в четыре маршрута. Изолированные проверки проходили, но большие живые запросы завершались по тайм-аутам: ранний отказ с отменой непрочитанного тела не доставлял HTTP 413. Журналы содержали WallClockTime при низком CPU. Это отдельная проблема обработки загрузок, а не подтверждённое продолжение старого зависшего запроса публикации.

В API 82 изменён только `body-reader.mjs`; остальные 67 файлов сохранены. После превышения 10 100 000 байт накопленные данные освобождаются, остаток конечного тела читается без сохранения и без запуска multipart-парсера, затем возвращается 413. Общий монотонный срок чтения — 45 секунд. Это обход ожидания раннего ответа транспортом; [upstream-проблема Supabase](https://github.com/supabase/edge-runtime/issues/737) описывает соответствующий механизм с клонированным потоком. Модель воспроизводит его, но внутреннее устройство управляемого relay не установлено. Количество переданных через транспорт байт не ограничено этим обходом; сохранение и разбор ограничены прежним лимитом, чтение ограничено по времени. Доставка ответа для незавершённого или бесконечного тела после отмены остаётся зависимой от провайдера; исправление relay не заявляется.

Рабочая проверка 4 ноября: 10 100 001 байт с точным Content-Length → **413 за 726 мс**; 10 300 000 байт без Content-Length, chunked → **413 за 882 мс**; малый некорректный multipart → 400. Все тела намеренно некорректны, реальные заказы, черновики, письма и прайс не создавались. 14 изолированных проверок прошли без пропусков: границы, память, срок чтения, модель relay, четыре настоящих маршрута, авторизация, обычный XLSX preview и вложения. Все 68 файлов API 82 скачаны и сверены. Подтверждения: [живая проверка](../work/upload-timeout/live-verification.json), [независимый разбор](../work/upload-timeout/independent-reader-validation.json), [маршруты](../work/upload-timeout/multipart-integration-result.json), [историческая диагностика API 81](../work/backlog-ready-release/multipart-live-diagnostic.json). Пункт закрыт для конечных загрузок; при изменении транспорта повторить этот контрольный набор, не подменять его проверкой бесконечного потока.

## Как обновлять реестр

1. Для каждого нового отложенного изменения добавить устойчивый ID, понятное название, затронутые части, место сохранения исходников, выполненные проверки, конкретную причину остановки и следующий шаг.
2. Разделять подготовку исходников, локальные проверки, публикацию исходников в ветку и включение в рабочей среде. Не обозначать все эти состояния словом «готово».
3. Зависший процесс отмечать отдельным блокером с датой, идентификатором запроса или процесса, затронутым каналом и последним подтверждённым состоянием. После успешного выпуска перепроверять старый блокер, а не переносить его автоматически.
4. Перед возобновлением перечитать текущие серверные исходники, версии и миграции, сверить `main`, совместить только нужные изменения и повторить необходимые проверки. Старый подготовленный пакет не должен откатить более поздние исправления.
5. После фактической публикации и проверки рабочего результата перевести пункт в опубликованные, записать коммит, версию и подтверждение. Не удалять историю причины остановки.

При инвентаризации сравнены 160 верхнеуровневых публичных файлов сайта и админки; [различия](../work/publication-backlog-audit/source-differences.json) и [добавленные локальные файлы](../work/publication-backlog-audit/local-files-absent-main.json) сохранены для повторной сверки. Само расхождение файла не считается отдельной неопубликованной функцией: локальный файл может быть старее рабочего или содержать несколько пакетов. Исторические заметки и неподтверждённые различия не выдаются за готовые выпуски.
