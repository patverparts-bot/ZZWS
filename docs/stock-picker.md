# Admin warehouse list selection

Model-code fallback treats dimensions/capacities such as `32mm` as specifications rather than product identifiers. A query for `Babyliss C459E 32mm titanium` can match `Babyliss C459E 32mm hair curler titanium` by its exact code despite extra descriptive words. Other 32mm products do not become candidates just because they share that dimension. Explicit conflicting dimensions are excluded.

The catalog includes a read-only stock picker for administrators with `price:read`, and a catalog-only check for clients. The catalog authentication lifecycle starts it after validating the account and resets it on logout/session expiry. The management dashboard does not load or mount the picker. It uses the existing authenticated `catalog` projection, including its admin-only raw `stockStatus` quantities and ordinary `wholesale` price. No backend changes, reservations, order creation or inventory mutations are involved.

Paste an Excel table or upload one-sheet XLSX/CSV/TSV/TXT (5 MB, 2000 data rows maximum). The example's two-column model/quantity format is supported, with or without Armenian headers. Russian/English headers and explicit article/model/quantity columns are also accepted. Article strings preserve leading zeros. Exact article or name matches take precedence. Next, the complete Latin brand/model token sequence is compared, ignoring surrounding Armenian/Russian category descriptions. This distinguishes Elica ERA C from HIDDEN/FOLD despite their shared IX/A/52 suffix, and PS5 Slim CD from Digital despite their shared PS5 token. The redundant PS5 token immediately before Playstation at the beginning is ignored on both sides of the full model comparison, so PS5 Playstation 5 Slim CD version matches Playstation 5 Slim CD version. A trailing /PS5 remains part of the model identity. Spacing around its slash is normalized. When an input explicitly starts with PS5 Playstation, its platform prefix may also match the catalog’s trailing /PS5 after the same complete model name. This handles DualSense Controller Chrome Teal with an Armenian category description and no suffix in the input. Every model/color token must still match; no console-to-controller substitution is defined. An input without either platform indication does not gain one. A descriptive multiword input never falls back to matching PS5 alone: console requests cannot produce a list of PS5 games. Standalone PS5 remains a generic model token. Only then are complete alphanumeric model tokens matched within the name. Ambiguous or unknown models remain visible for correction; ambiguous rows list every matching catalog name and article so the administrator can replace the input with an exact article. There is no substring guessing.

Each calculation fetches current catalog data. Allocation consumes a shared pool across repeated input rows. First it looks for a main warehouse that can supply the whole requested quantity, checking **003, 023, 031, 026** in that order. If none can supply the whole quantity, it splits between those main warehouses in that order, followed by the remaining warehouses starting with the largest stock. Shop stocks are reduced towards a common remaining level; ties use ascending warehouse code. This avoids leaving a single unit where the request can be fulfilled while retaining at least two units. When quantities require it, a shop may be reduced to one unit. Other warehouses retain one unit per article unless the initially unchecked “use last store unit” control is enabled. Incomplete/malformed stock descriptions are not guessed. Insufficient availability produces a shortage column. Missing/nonpositive wholesale prices export as empty cells. Unmatched input is retained.

Changing input or the switch clears the prior result; press the build button again to refresh. The table shows each warehouse allocation on its own row, repeating the article, model and unit price. Requested quantity and total shortage appear only on the first row of each input item so totals are not duplicated. Selected quantity is the quantity from that row’s warehouse. Items without allocations still have a row. Excel follows the owner’s six-column Russian import layout, independent of UI language: Артикул, Номенклатура, Характеристика, Количество, Цена, Склад. Характеристика is blank. Each allocation has its own row with that warehouse’s quantity. All available warehouse allocations export first. After a blank separator, a labeled shortage block uses only three columns: Код, Модель, Недостающее количество. It includes missing catalog items, zero-stock items and only the unallocated remainder of partially filled items. No price or warehouse cells are written in this block, regardless of original input order; invalid quantities remain blank. Article and warehouse codes are text (leading zeros retained), quantities/prices are numeric and absent prices are blank. Column widths are set for readability. It exports values only, never input formulas. No result or input is saved to browser storage. Session reset invalidates pending work and clears all inputs, results and the switch.

Files: `js/warehouse-allocation.js` (pure parser/matcher/allocation), `admin/stock-picker.js` (input, authenticated reads, results and Excel), `admin/stock-picker-i18n.js` (Armenian/Russian labels loaded before the existing localization engine), `admin/index.html` (script registration), `admin/app.js` (session lifecycle).

Validation: `node tests/warehouse-allocation.cjs`; `node tests/ui/stock-picker.cjs` with installed Playwright/Edge. UI checks use a synthetic catalog and exercise pasted tables, XLSX, the last-unit control, export, account reset during a request, denied client access, Russian localization and a 390px viewport. No production orders or stock are changed.

The Dealer/KP price switch defaults to Dealer and resets on session exit. Dealer uses the existing admin catalog wholesale field; KP uses kpPrice (the admin catalog already chooses KP promo over ordinary KP). Missing selected prices remain blank; there is no automatic fallback to the other price group. Changing the switch invalidates results and pending reads, requiring a fresh calculation. This changes only displayed/exported unit prices, never matching, quantities, warehouse allocation or order data. The shortage export remains price-free.

Local catalog preview: the same stock-picker module also mounts in a native dialog opened by an admin-only button beside the catalog heading. The storefront authentication lifecycle starts/resets it; it always reads the administrator catalog via secureApi, independently of customer-view filters. Closing the dialog preserves the current work; session reset closes it and erases inputs/results. The old price-section entry has been removed; the picker is accessed only from the catalog. Styling lives in admin/stock-picker-catalog.css. Integration checks in tests/ui/stock-picker-catalog.cjs use an in-memory server and cover dialog, permission gating, KP, export, Escape, mobile and logout. Screenshots in output/stock-picker/catalog-*.png show synthetic catalog data.

Catalog visual results: after a successful calculation, Show found products closes the picker and displays only uniquely matched articles using the normal product cards/photo/details system. Duplicate list rows yield one card; unresolved candidates are not shown as matches. A visible notice offers Return to full catalog. Existing filter values are preserved and temporarily bypassed for this explicit view, and are reapplied on return. The scope always stays within the current authorized allProducts projection. Calculations and Excel remain in the picker when reopened. Editing input/recalculating clears the visual selection; logout clears it without rendering private data. The visual state is not persisted. Integration tests verify filtering, card view, preserving calculations and restoring a restrictive original search.

Client and cart modes: authenticated clients can open the same catalog dialog, with no warehouse controls, stock codes or Dealer/KP selection. Matching uses only their server-projected catalog and effective wholesale field. Results are grouped as Available, Clarify availability, and Absent from your catalog. Clarify availability remains a distinct status and is transferable too; no numerical stock quantity is inferred for clients. Client Excel uses only their prices with no warehouse column, plus separate price-free pending and absent sections.

The catalog dialog has Transfer to cart for both administrators and clients. Admin transfer uses the sum allocated across all warehouses for each article; client transfer uses requested quantities of matched, priced catalog products, including Clarify availability. Duplicate input rows are aggregated by article, added to existing basket quantities via the existing setDirectQty flow, and capped at MAX_QTY. Current normal checkout pricing and order data structures remain authoritative. A fresh authorized catalog read precedes transfer; disappeared/ambiguous products cannot be added and admin quantities cannot grow beyond the reviewed allocation. A successful transfer disables repeat submission until recalculation. Session/input changes invalidate pending work. No orders are submitted automatically.
